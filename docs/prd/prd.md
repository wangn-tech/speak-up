# 背景、问题与目标

## 用户问题

成年英语学习者普遍存在「开口难、无反馈、难坚持」三类问题（以下为需求假设，需在 MVP 验证阶段以用户访谈与行为数据校准）：

- 缺乏练习语境：生活中缺少与真实对象进行英语对话的机会，开口场景少；
- 反馈不及时：自练难以发现发音、语法与表达问题，进步感知弱；
- 难以坚持：练习枯燥、无目标感，缺少数据化的进步反馈与复习牵引。

## 产品定位

面向成人的 AI 英语口语陪练 Web 产品：以「场景化语音对话」为核心，提供「练习—反馈—复盘」闭环，让用户随时开口、及时获得个性化反馈、并看到长期进步。差异化价值集中体现在后端与 AI 端：场景对话编排（场景即状态机）与证据式复盘编排，以及支撑二者的 Agent 与 RAG 体系。

## 非目标（本期不做）

- 不做移动端原生 App：一期以 Web 为主，移动端仅保证可用性，PWA 化留待后续；
- 不做真人外教、直播课、班级小组：产品形态为纯 AI 陪练；
- 不做系统化语法课程：以练带学，语法讲解以内联反馈形式出现；
- 不做写作批改等非口语内容；
- 不做复杂会员权益体系：一期仅保留免费模式与付费入口占位，商业化在 MVP 验证后另行立项。

# 用户与核心场景

## 目标用户画像

| 画像 | 典型特征 | 核心诉求 | 典型练习方式 |
|-|-|-|-|
| 备考族（雅思 / 托福 / 四六级口语） | 有明确考试时间与题型压力 | 按题型与评分维度练习，获得接近考试的模拟体验 | 每晚 20-30 分钟模拟面试、雅思 Part 1-3 |
| 职场人（外企 / 跨境业务） | 需要英文开会、面试、汇报 | 商务场景演练与表达润色 | 通勤或午休完成一次 10-15 分钟场景练习 |
| 兴趣学习者 | 旅行、社交、日常交流需求 | 轻松场景对话、敢开口 | 碎片时间 5-10 分钟生活场景练习 |

## 核心使用场景

**场景一：碎片时间场景练习**

- 用户：职场人小李；任务：在午休完成一次「机场值机」练习；
- 关键路径：门户登录 → 工作台 → 场景广场筛选「旅行」→ 选择「机场值机」→ 查看场景介绍 → 开始语音对话 → 结束 → 查看反馈；
- 成功表现：完成 3 分钟对话，获得评分与 2-3 条具体改进建议，练习被记录。

**场景二：备考模拟面试**

- 用户：备考族小张；任务：完成一轮模拟面试并获取逐题反馈；
- 关键路径：选择「英文面试」→ 进入模拟面试 → 多轮问答 → 结束 → 查看逐题反馈与总分；
- 成功表现：得到逐题评分与建议，并看到与上次模拟的对比。

**场景三：周期复盘**

- 用户：备考族小张；任务：查看一周练习趋势并安排下周练习；
- 关键路径：复盘中心 → 趋势页 → 薄弱点清单 → 复习计划（错题本 + 推荐场景）；
- 成功表现：明确薄弱维度与推荐练习，可一键进入推荐场景。

# 功能需求

本节按关键功能描述行为需求与验收。每条验收遵循「前置条件 — 触发动作 — 可观察结果」，并给出与主要风险对应的失败与边界场景。

## FR1 门户网站与账号体系

门户网站是公开入口，承载品牌介绍、功能亮点、场景示例与登录注册；账号体系支撑登录态与个性化数据。

行为需求：

- 门户页包含产品介绍、核心功能亮点（语音对话 / 场景练习 / 个性化反馈 / 练习复盘）、场景示例、登录与注册入口；定价信息在商业化确定后补充，当前仅占位；
- 支持注册与登录：手机号 + 验证码、邮箱 + 密码（首发至少一种，第三方登录待定）；未登录访问主应用时跳转登录页，登录后回到原目标页；
- 登录态过期：接口返回 401，前端引导重新登录，不丢失已保存的练习记录。

验收：

- 成功场景：给定未登录用户访问门户 → 点击「开始练习」→ 跳转登录页 → 用户完成注册并登录 → 进入工作台并展示练习入口；
- 失败场景：给定用户输入错误验证码 → 提示校验失败并允许 60 秒间隔后重发，不进入主流程；
- 边界场景：给定登录态过期用户停留在对话页 → 保存会话草稿并提示重新登录，重新登录后可继续或重新开始。

## FR2 主页面（工作台）

登录后的主页面围绕「今天练什么、练得怎样、接下来练什么」组织。

行为需求：

- 展示练习概览：连续练习天数、本周练习时长、最近一次总分；数据缺失时展示引导文案而非默认值；
- 主入口：开始新练习（推荐场景 / 继续上次）、场景广场、复盘中心、个人中心；
- 「今日推荐」：一期按最近练习场景、薄弱维度与场景难度推荐 1 个场景；推荐规则上线后按点击与完成数据调优；
- 新用户无数据时展示默认引导（选择场景开始第一次练习）。

验收：

- 成功场景：给定已完成 1 次练习的用户登录 → 工作台展示最近总分与「今日推荐」→ 点击推荐卡片进入场景详情；
- 失败场景：给定新用户无练习数据 → 工作台不展示空评分，仅展示「开始第一次练习」引导。

## FR3 场景练习

场景是练习的基本单元，由「背景设定 + 角色 + 目标 + 剧情阶段」构成，AI 角色按状态机驱动对话（编排机制见「亮点设计」）。

行为需求：

- 场景广场：按分类（生活旅行 / 职场 / 考试 / 社交）与难度筛选；场景卡片展示标题、简介、预计时长、难度；一期上线 ≥8 个场景，其中 ≥2 个支持剧情分支（P1 扩展）；
- 场景详情页：展示背景设定、角色介绍、练习目标与开始按钮；
- 练习过程：用户与 AI 角色对话，界面提供「结束练习」；AI 按场景状态机推进剧情，并在检查点判定目标是否达成；
- 中断恢复：练习中途离开（网络中断 / 页面关闭）时保存会话草稿，可继续或放弃；放弃不产生评分；
- 目标达成：结束练习时展示是否达成场景目标（如「完成点餐并成功结账」），作为反馈报告的组成部分。

验收：

- 成功场景：给定用户选择「餐厅点餐」场景并开始 → 完成 ≥3 轮有效对话并主动结束 → 生成练习记录（对话文本 + 语音 + 评分），并显示场景目标达成结果；
- 失败场景：给定练习中网络中断 → 会话保存为草稿，重新连接后可继续；中断超过 24 小时自动转为「未完成」记录，不参与评分；
- 边界场景：给定用户连续 2 次无有效语音输入 → 系统给出提示与示例表达（卡壳救援），不无限等待。

## FR4 语音对话

实时对话是核心交互。一期采用半双工（用户说完 → AI 回复），打断能力列入 P1。

行为需求：

- 输入：浏览器麦克风采集，支持 VAD 自动断句与按住说话两种模式；同时支持文字输入作为兜底；
- 输出：AI 回复以流式文字呈现，同时进行 TTS 语音朗读（可开关、可调语速）；
- 转写展示：用户语音实时转写并展示在对话区；转写错误允许用户以文字修正（P1）；
- 异常处理：静音超时（如 10 秒）给出提示；识别失败提示重说；AI 回复超时展示「正在思考」状态并支持重试；
- 数据：对话音频与文本按会话落库，用于反馈与复盘。

验收：

- 成功场景：给定用户已授权麦克风并开始练习 → 用户说完一句话（停顿 ≥0.8 秒或点击停止）→ 在目标延迟内返回 AI 首句文字并开始合成语音（延迟目标见「非功能需求」）；
- 失败场景：给定麦克风权限被拒绝 → 页面提示授权引导，同时提供文字输入模式，不阻塞练习；
- 边界场景：给定用户长时间静音 → 10 秒后出现提示并播放 AI 引导语，避免冷场。

## FR5 个性化反馈

每次练习生成「实时轻量 + 结束完整」两级反馈。完整反馈异步生成，通过 Kafka 触发，用户可在反馈页查看。

行为需求：

- 综合评分：总分（百分制）与分维度分：发音、语法、词汇、流利度、逻辑结构；评分口径（维度权重与量尺）在技术方案中固化并随版本说明；
- 逐句反馈：对用户每一句的纠错、更自然的表达建议、发音问题，绑定时间戳，可点击回听原句；
- 实时轻量反馈：练习中 AI 对明显错误进行内联提示，不打断对话流畅度，频率受限（如每句最多 1 条）；
- 个性化：反馈结合用户历史画像（P1 起经 RAG 注入），优先指出与既往薄弱点相关的改进；
- 反馈状态：练习结束后展示「生成中 / 已生成 / 生成失败（可重试）」。

验收：

- 成功场景：给定用户完成练习 → 反馈生成完成后进入反馈页 → 展示总分、5 个维度分、逐句问题列表（每条含原句、建议、时间戳，可回听）；
- 失败场景：给定发音评估服务不可用 → 发音维度标记「待补充」，总分基于其余维度计算并注明，不阻塞其他反馈展示；
- 边界场景：给定转写为空（用户未说话）→ 不生成评分，提示「本次练习未检测到有效语音」。

## FR6 练习复盘

复盘把「一次练习」升级为「一段进步」，包含历史列表、单次详情、趋势分析与复习计划。

行为需求：

- 复盘中心：按时间倒序展示历史练习（场景、时间、总分、目标达成），支持按场景 / 维度筛选；
- 复盘详情：对话回放（文本 + 语音）、逐句诊断、本次亮点与问题归纳、评分明细；
- 趋势分析：按时间展示总分与各维度分趋势并标注明显变化；数据不足（少于 2 条）时提示「继续练习后可查看趋势」；
- 复习计划：错题本（自动沉淀逐句反馈中的高频问题，去重并按频次排序）；推荐下次练习场景 / 题目（结合薄弱维度与偏好）；间隔复习提醒（P1 起，提醒方式待定）；
- 复盘内容由离线管线生成，生成结果支持用户标记「有帮助 / 无帮助」用于质量调优。

验收：

- 成功场景：给定用户完成 ≥2 次同一维度（如发音）练习 → 进入复盘中心趋势页 → 展示该维度得分变化与薄弱点描述；
- 失败场景：给定复盘生成任务失败 → 页面展示「复盘生成中 / 失败，可重试」，不展示空壳数据；
- 边界场景：给定用户仅 1 次练习 → 趋势区展示「数据不足」引导，其余功能（历史、详情）正常可用。

# 亮点设计（后端与 AI 端）

本产品的差异化集中在后端与 AI 端：场景对话编排与复盘编排是两项核心能力，分别由 LangGraph 状态机与异步管线支撑；Agent 与 RAG 是底层支撑，本节给出需求分析。

## 对话场景编排：场景即状态机

场景被建模为一张有向状态图，AI 角色按图推进剧情，同时保留对话开放性（阶段节点内部为自由对话，图层面约束剧情主线）。这样既保证练习不跑题、目标可达，又避免脚本化死板。

场景定义要素：

- 角色卡：性格、语气、背景、知识边界（只答场景相关内容）；场景知识经 RAG 注入，保证角色一致性；
- 剧情阶段：开场、主线阶段、检查点、收尾；每个阶段定义 AI 行为指令与推进条件；
- 目标与判定：场景目标在检查点由规则 + LLM 双重判定，判定结果进入反馈；
- 分支（P1）：支持 2-3 条剧情分支，按用户输入选择，提升复练新鲜感。

三层对话控制：

- 会话层（后端）：会话创建、鉴权、限流、连接管理与音频流转发；
- 编排层（AI 服务）：LangGraph 状态机维护剧情进度；意图识别（继续剧情 / 求助 / 换题 / 结束 / 闲聊）路由下一步；记忆更新；
- 模型层：LLM 生成 + RAG 检索；生成前进行内容安全审核。

自适应与救援：

- 难度自适应：实时评估词汇等级、句长、错误密度，调节 AI 语速指示、用词复杂度、追问深度与提示频率；连续表现提升后逐级上调；
- 卡壳救援：静音超时 / 求助 / 冷场时主动提问、换话题或提供中文提示；连续 2 次卡壳自动降一档难度；
- 记忆：短期记忆（本场剧情进度与最近轮次）+ 长期用户画像（经 RAG）。

## 复盘编排：证据式异步管线

复盘是「一次练习」到「持续进步」的桥梁，通过 Kafka 异步解耦，不占用对话链路资源。

管线步骤：

- 触发：会话结束 → 后端发布事件到 Kafka → 复盘 Worker（LangGraph 编排）消费；
- 转写对齐：ASR 文本、时间戳、语音分句对齐，形成结构化对话记录；
- 并行评估：发音 / 语法 / 词汇 / 流利度 / 逻辑 5 个评估子任务并行执行（LangGraph 并行节点）；
- 聚合评分：维度加权汇总 + 置信度，产出总分与维度分（权重在技术方案固化）；
- 证据标注：每条反馈绑定原句与时间戳，支持点击回听（证据式反馈，可追溯）；
- 报告生成：LLM 生成自然语言总结（亮点、问题、改进方向）；
- 趋势与复习计划：结合用户历史画像（RAG），生成趋势、错题本与推荐；
- 写入与通知：评估 / 报告落库、错题本更新、通知用户（站内）。

失败与降级策略：

- 单个评估维度失败 → 该维度标记「待补充」，不阻塞整体复盘；
- 节点失败 → 按节点配置重试（默认最多 3 次，指数退避）→ 仍失败则降级跳过并在报告中标注；
- 整体超时 → 进入补偿队列延迟重跑，用户侧先展示「复盘生成中」；
- 写入失败 → 告警并保留原始评估数据，支持幂等重跑，避免重复计分。

## Agent 需求分析

系统由四类 Agent 承担职责，均以 LangGraph 编排，具备明确的状态、记忆、工具与失败处理契约。

| Agent | 触发时机 | 核心输入 | 核心输出 | 状态与记忆 | 工具 / 依赖 | 失败处理 | 质量指标 |
|-|-|-|-|-|-|-|-|
| 角色扮演 Agent | 实时（每轮对话） | 当前轮用户输入、场景状态、记忆、检索结果 | 角色回复文本 + 剧情推进动作 | 会话记忆 + 场景状态机位置 + 长期画像（RAG） | LLM、RAG 检索、TTS、内容安全审核 | 回复超时降级为通用引导语并提示 | 角色一致性、剧情任务完成率、对话轮次 |
| 意图识别 Agent | 实时（每轮对话） | 用户输入 + 最近上下文 | 意图标签 + 置信度 | 无状态 | 轻量 LLM | 低置信默认「继续剧情」 | 意图识别准确率（抽样） |
| 反馈 Agent | 离线（会话结束异步） | 转写文本、音频特征、时间戳 | 结构化评估（评分、问题、建议） | 只读用户画像 | LLM、发音评估服务、词典 | 单维度失败标记「待补充」 | 建议可采纳率、评分与人工标注一致性 |
| 复盘 Agent | 离线（异步） | 本次评估 + 用户历史（RAG） | 报告文本、趋势、错题、推荐 | 读用户画像与历史评估 | LLM、RAG 检索 | 生成失败可重试，保留部分结果 | 报告有用性反馈、推荐点击率 |

### 编排模式：ReAct 在线循环 + DAG 离线管线（LangGraph）

按延迟约束分两类编排模式，均以 LangGraph StateGraph 承载：

| 编排模式 | 适用 Agent | LangGraph 实现与约束 |
|-|-|-|
| ReAct 循环（在线实时） | 角色扮演 Agent、意图识别 Agent | 循环边 + ToolNode：Thought → Action（RAG 检索 / 记忆读写 / 内容安全审核 / 词典查询）→ Observation → Reply；约束：工具白名单、单轮最大步数 ≤3、每次工具调用超时与重试上限、循环超限降级为通用引导语 |
| DAG 管线（离线异步） | 反馈 Agent、复盘 Agent | 并行分支 + 条件边 + 汇合 reduce：发音评测 / 语法纠错 / 流畅度 / 内容质量等节点并行执行后聚合；单节点失败隔离标记「待补充」，不阻塞整体管线；幂等执行保证不重复计分与写入 |

两类模式共用同一状态 Schema 与可观测基础设施：每步的输入输出摘要、延迟、错误、token 消耗写入结构化日志并上报 Prometheus 指标；超时、幂等、重试为图内声明式配置。在线 ReAct 会话经 gRPC ConversationService 流式暴露，离线 DAG 任务经 EvaluationService / ReviewService 提交与查询（详见 7.5）。

Agent 基础设施要求：

- LLM 统一网关：模型路由（按任务选择模型与参数）、限流、超时、降级、成本与日志统计；
- 记忆管理：短期记忆限长（如最近 10 轮）+ 摘要压缩；长期记忆经 RAG 存取，支持用户级隔离；
- 内容安全：所有生成内容过安全审核，违规内容拦截与替换并记录；
- 可观测：每个 Agent 的输入输出摘要、延迟、错误、token 消耗写入结构化日志并上报 Prometheus 指标；
- 幂等与重试：异步 Agent 支持幂等执行与重试，保证不重复计分、不重复写入。

## RAG 需求分析

RAG 用于解决三类问题：角色一致性（场景知识）、反馈有依据（学习资源）、个性化（用户画像）。三类知识库统一走同一检索链路，按场景限定知识域。

| 知识库 | 内容 | 主要使用方 | 使用时机 | 更新方式 |
|-|-|-|-|-|
| 场景知识库 | 场景脚本、角色卡、常用表达、文化背景 | 角色扮演 Agent | 对话时检索 | 内容审核后发布上线，重建索引 |
| 学习资源库 | 语法点、词汇表、范文 | 反馈 Agent、复盘 Agent | 反馈 / 复盘时检索 | 内容团队维护，审核上线 |
| 用户个性化库 | 历史错误、偏好话题、掌握进度、复习状态 | 角色扮演、反馈、复盘 Agent | 对话 / 反馈 / 复盘时检索 | 会话结束后 Kafka 异步增量写入 |

检索链路（离线 + 在线）：

- 离线：知识源 → 文档切分（保留来源元数据）→ Embedding 向量化 → 向量库（向量索引 + 关键词索引 + 元数据过滤）；
- 在线：查询构造（Agent 上下文）→ 混合召回（向量 + 关键词，按场景限定知识域）→ 重排 → 截取 Top-K → 注入 Prompt（带引用标记，限定只用检索内容作答）→ LLM 生成 → 引用可溯源；
- 用户画像库按用户隔离，跨用户不可检索；画像数据随账号注销一并删除。

质量与评估：

- 检索延迟预算：对话链路 ≤300ms，反馈 / 复盘 ≤1s（目标值，待压测校准）；
- 质量指标：召回相关性、引用忠实度、幻觉率；建立离线评测集 + 在线抽样标注；
- 切分策略、Embedding 模型与向量库选型（pgvector / Milvus）在技术方案阶段确定，数据规模是主要选型变量。

# 系统架构与技术方案

> 📌 设计图（交互式，浏览器打开）：[系统总体架构](diagrams/01-architecture.html)

## 总体架构

- 客户端：门户网站与主应用，React + TypeScript，浏览器端渲染，经 CDN / Nginx 接入；
- 接入层：API 网关统一鉴权（JWT）、限流、路由与请求日志；
- 后端服务：Go + Gin，负责认证、用户、场景、会话、反馈、复盘业务与配置；WebSocket 会话管理与音频流代理；
- AI 服务：Python + FastAPI + LangGraph，承载对话 Agent、反馈管线、复盘管线与 RAG 检索；
- 数据层：MySQL（业务数据）、Redis（会话状态 / 缓存 / 限流）、Kafka（事件总线）、向量库（RAG，首推 Qdrant，见开放问题 Q3）、对象存储（音频，加密存储）；
- 可观测：Prometheus 采集服务指标 + Grafana 看板与告警（MVP 不引入 ELK）；
- 部署：Docker Compose 编排开发与单机环境；生产环境 K8s 列入二期。

## 通信与集成决策

> 关键决策：AI 服务不直接暴露给前端，统一经后端以 gRPC 接入。理由：① 统一鉴权与限流，模型密钥与内部能力不落地浏览器端；② 后端作为编排入口，便于会话状态管理、任务下发与审计；③ 全链路可观测（gRPC 链路追踪）；④ 前端协议单一（REST + WebSocket），AI 服务内部演进不影响前端。该决策为产品与架构共同决定，若后续出现纯浏览器端低延迟诉求（如直连 TTS 边缘节点），作为优化项另行评估。

- 前端 ↔ 后端：REST（业务接口）+ WebSocket（音频流式上传、事件下行、TTS 流式回传）；
- 后端 ↔ AI 服务：后端为 gRPC 客户端、AI 端为 gRPC 服务端（对话推理、RAG 检索、评估 / 复盘任务提交）；后端单进程双协议（Gin 管 REST / WebSocket 面向前端，gRPC 管 AI 互联）；离线结果经 Kafka 事件回写，不反向调用；protobuf 契约单独维护版本；
- 异步链路：会话结束、行为埋点等事件写入 Kafka；反馈、复盘、用户画像更新由 Worker 消费；
- 对话链路：音频流式上传 → ASR（阿里云百炼 paraformer 实时流式，见第 12 章选型定稿）→ 编排层生成回复 → 流式回传文字 + TTS。

## 关键接口与协议

- REST：/api/v1/auth/\*（注册、登录、刷新）、/api/v1/scenes/\*（列表、详情）、/api/v1/sessions/\*（创建、结束、草稿）、/api/v1/evaluations/\*（查询）、/api/v1/reviews/\*（复盘）、/api/v1/profiles/\*（个人中心）；
- WebSocket：/ws/conversation（音频上行、事件下行：转写片段、回复流、TTS 流、状态事件）；
- gRPC（内部）：ConversationService（对话推理，ReAct 会话流式）、RetrievalService（RAG 检索）、EvaluationService（反馈 DAG 任务触发 / 查询）、ReviewService（复盘 DAG 任务触发 / 查询）；proto 契约独立版本管理。

## 部署与运维

- 开发 / 单机：Docker Compose 一键编排全部组件（MySQL、Redis、Kafka、向量库、AI 服务、后端），本地 .env 管理配置；
- 生产（二期）：K8s 部署，AI 服务按对话并发水平扩展，Worker 按任务积压扩展；
- 环境隔离：dev / staging / prod 三套环境，配置与密钥走环境变量与密钥管理，不落仓库；
- 灰度：AI 能力（对话、反馈）支持按用户 / 流量灰度，配合可观测指标回滚。

## 安全与合规

- 音频数据：传输 TLS，存储加密（对象存储服务端加密），访问按用户与角色鉴权；用户注销时音频与画像数据一并删除；
- 内容安全：AI 生成内容与用户输入均过安全审核，违规内容按策略处理并建立审核日志；
- 未成年人：注册流程校验年龄或提供监护人同意机制（具体方案按合规要求确认，见开放问题 Q4）；
- 隐私：发布隐私政策，录音前取得用户明确授权，提供数据导出与删除入口；
- 账号安全：密码摘要存储、验证码防刷、登录限流、异常登录提醒（P1）。

## 可用性与降级

- AI 服务不可用：对话页提示稍后重试并保留会话草稿，门户与历史记录等能力不受影响；
- 反馈 / 复盘延迟：展示「生成中」状态，不阻塞其他功能；
- ASR / TTS 单点故障：降级为文字对话模式（文字输入 + 文字回复）；
- 关键路径依赖（登录、场景列表）具备超时与重试，失败提示明确。

## 可观测性

- 日志：结构化日志（服务、链路 ID、耗时、错误码）输出 stdout 由容器统一采集；MVP 阶段使用 Docker 日志即可，规模化后再引入日志平台（如 Loki / 云日志）；
- 指标：请求量、延迟分位、错误率、Kafka 积压、AI token 消耗与成本、并发在线会话；Go 与 AI 服务分别暴露 /metrics，由 Prometheus 定时采集；
- 追踪：gRPC / WebSocket 链路追踪，贯通前端 → 网关 → 后端 → AI 服务；
- 告警：基于 Prometheus 规则的错误率 / 延迟 / 积压告警，经 Grafana / Alertmanager 通知，复盘任务失败率单独监控。

## A.3 SDK 与生态统一性

- **【已确认事实】**百炼提供官方 Python **dashscope** SDK，ASR（paraformer）与 TTS（SpeechSynthesizer）同一 SDK、同一 DASHSCOPE_API_KEY，与现有通义百炼 LLM 调用一致，FastAPI 可直接复用密钥管理与限流网关。
- **【建议】**火山豆包语音官方文档以 WebSocket 协议 + 控制台 X-Api-Key/Resource-Id 为主，Python 侧可用官方 SDK 或社区包（如 doubao-speech）直连 WebSocket，工程成本略高于 dashscope。
- **【建议】**讯飞、腾讯云均需独立账号、独立鉴权与独立 SDK，与通义百炼生态割裂，仅作容灾/对比备选，不进入主链路。

# ===== 阿里云百炼：LLM / ASR / TTS 共用同一密钥 =====

# ----- TTS（首推：阿里云百炼）-----
TTS_PROVIDER=aliyun
TTS_MODEL=cosyvoice-v2             # 流式语音合成（WebSocket）
TTS_VOICE=longanyang               # 音色，控制台大模型音色列表替换
TTS_FORMAT=mp3
TTS_SAMPLE_RATE=24000
TTS_RATE=1.0                       # 语速，PRD 要求可调

# ----- 备选：火山引擎豆包语音（异构容灾 / 效果对比，非主链路）-----

VOLC_RESOURCE_ID_ASR=volc.bigasr.sauc.direct   # 流式 ASR，以控制台 ResourceId 为准
VOLC_TTS_VOICE_TYPE=zh_female_linjianvhai_moon_bigtts
